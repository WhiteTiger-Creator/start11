Two things have to hold of `/app` at the end: `/app/data/compacted_base.jsonl` and `/app/data/manifest_repaired.json` describe the whole tree that is on disk, and `/app/workflow/rebuild_index.py` is a program whose behaviour is the deployed release's, so that a run of it produces the three artifacts `/app/docs/index_contract.json` names. The rest of this is where those come from and what has to be true of them.

A compaction was interrupted mid-run. Twelve segment files under `/app/data/pending` reached disk but were never linked into `/app/data/manifest.json`, and the compactor stopped part-way, so `/app/data/compacted_base.jsonl` and `/app/data/manifest_repaired.json` both stop short of the tree that is actually on disk. Which unlinked segments may be admitted at all, where they enter the tree and how they are numbered, which version of a key survives, how keys collate and what a delete leaves behind are decisions the deployed release makes rather than yours, and every shard boundary and every plan is wrong until the base and the repaired manifest are rebuilt. Both are rewritten in place, at the paths they already occupy: `/app/data/compacted_base.jsonl` holds the whole reconciled base and `/app/data/manifest_repaired.json` the whole repaired manifest, each replacing what ships there rather than adding to it. Whatever you reconcile them with is yours to keep or throw away; of that step, only those two files are graded. The segment files themselves are evidence: those under `/app/data/pending` and `/app/data/segments` stay where they are and as they are, and a segment is linked by what the repaired manifest says about it rather than by being moved. `/app/data/manifest.json` is evidence of the same kind: it is the record of what the tree held when the compaction stopped, which is what the repaired manifest is repaired against, so it too comes back byte for byte unchanged.

`/app/workflow/rebuild_index.py` was carried over from a migration trial and implements a branch this node is not on; what it has to be instead is the program described here. It carries `--input` and `--output-dir` with the defaults it already documents, and the repaired manifest and `/app/data/index_policy.json` always come from their fixed absolute paths; `--input` selects the base alone. The contract names the policy's operational fields and says what each one means, and every one of those is an input the rebuild honours; anything else the policy carries is there to be read by people rather than acted on. `/app/docs/index_contract.json` is the output contract: paths, schemas, required fields, types and sort orders. It says nothing about how any value is derived. Reconstruct that from `/app/docs/release_notes`, which carries every release the product has shipped; the manifest records which one this node runs, and notes published after it describe behaviour this node must not have. A run writes exactly the three artifacts the contract names -- `/app/output/summary.json`, `/app/output/shard_index.json` and `/app/output/compaction_plan.jsonl` where the flag is not given, and those same three names in the directory `--output-dir` selects where it is -- and nothing else into it: standard library only and every module named outright in the source rather than assembled at run time, with the work done in the interpreter that runs it rather than handed to another program or a second interpreter, identical across reruns, correct on any base that conforms to the contract rather than on the graded one alone, inside the contract's 120-second budget, and leaving the frozen snapshot `/app/workflow/.rebuild_index.original` exactly as it is. The rule documents are what this work is done from rather than things it writes, so `/app/docs/index_contract.json` and every file under `/app/docs/release_notes` come back byte for byte unchanged.
